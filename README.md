# Luminalix

An agent that detects **blind spots in global disease surveillance** by
cross-referencing three signals per region:

1. **Official survey data** — slow, authoritative, goes stale
2. **Hospital admissions data** — fast-moving proxy signal
3. **Resource allocation data** — funding / staff / vaccine stock

The agent flags regions where survey data is stale **AND** admissions trends
suggest an emerging risk **AND** resources are inadequate, writes a justified
vulnerability assessment back into DataHub as an annotation, and serves the
results through a React web app.

Built for the **Build with DataHub: The Agent Hackathon**.

## Architecture

```
DataHub Instance  ◄────►  MCP Server (mcp-server-datahub)
                             │
                             ▼
                    FastAPI Backend  ──►  data/latest_report.json
                    (agent orchestrator,      (JSON persistence)
                     Gemini reasoning,
                     REST endpoints)
                             │  JSON / REST
                             ▼
                    TypeScript React frontend
                    (regions list + detail view)
```

- **Backend**: Python + FastAPI (`backend/`)
- **Reasoning**: Gemini via Google Vertex AI (`google-genai` SDK, `backend/app/agent/reasoning.py`)
- **Data platform**: DataHub (GMS v1.7.0) via the DataHub MCP server —
  dataset-level schema / freshness / lineage reads **and** write-back of
  findings as dataset annotations
- **Region-level data**: SQLite directly (`data/luminalix.db` via
  `backend/app/agent/data_access.py`) — DataHub's MCP tools don't return
  row-level data, so region values come from the database, the same role a
  warehouse client would play alongside DataHub in production
- **Persistence**: a single JSON file, `data/latest_report.json`
- **Frontend**: React + TypeScript, built with Vite, styled with Tailwind CSS (`frontend/`)

## Backend setup

Requires Python 3.11+.

```bash
cd backend
python -m venv .venv
.venv\Scripts\activate        # Windows (use `source .venv/bin/activate` on macOS/Linux)
pip install -r requirements.txt
copy .env.example .env        # Windows (use `cp` on macOS/Linux)
# then edit .env and set VERTEX_PROJECT (see below)
```

### Vertex AI is required

Luminalix calls Gemini through **Google Cloud Vertex AI** — not the Gemini
Developer API. The Developer API free tier was evaluated and found
insufficient for a full run: the legacy `gemini-2.5-flash` model returns
`404` ("no longer available to new users"), `gemini-2.0-flash` has a `429`
free-tier quota of `0`, and `gemini-3.5-flash` — the only working Developer
API model — hits free-tier rate limits (~5 requests/minute) partway through
a ~30-region run. Vertex AI is the only path that completes a full run, so
it's the backend the app is built on.

Set up the Google Cloud side once:

1. Install the [Google Cloud CLI](https://cloud.google.com/sdk/docs/install).
2. Authenticate and pick your project:
   ```bash
   gcloud init
   ```
   Follow the prompt to log in and set your GCP project.
3. Set up **Application Default Credentials (ADC)** — the agent authenticates
   to Vertex AI with ADC, not an API key:
   ```bash
   gcloud auth application-default login
   ```
4. Enable the Vertex AI API (in the console it may display as **"Agent
   Platform API"**):
   ```bash
   gcloud services enable aiplatform.googleapis.com --project=<your_gcp_project_id>
   ```
5. **Verify model availability in YOUR project.** Vertex AI model availability
   varies per project. In the Cloud console, open **Model Garden** and confirm
   `gemini-3.5-flash` is available to your project. (It is confirmed available
   in the `luminalix-v1` project.) If it isn't listed, pick a model that is and
   set `GEMINI_MODEL` accordingly in `backend/.env`.
6. Give your account `roles/aiplatform.user` (or equivalent) on the project.

Then configure `backend/.env`:

```bash
# backend/.env
VERTEX_PROJECT=<your_gcp_project_id>
VERTEX_LOCATION=global      # use "global" — some newer models are global-endpoint-only
GEMINI_MODEL=gemini-3.5-flash
```

> `VERTEX_LOCATION` defaults to `global`. Don't set it to `us-central1` — some
> newer Gemini models are only served on the global endpoint.

Run the API (from the `backend/` directory):

```bash
uvicorn app.main:app --reload --port 8000
```

Interactive docs: <http://localhost:8000/docs>

Run the tests (from the `backend/` directory):

```bash
pytest
```

## Frontend setup

Requires Node.js 18+.

```bash
cd frontend
npm install
npm run dev
```

Open <http://localhost:5173>. The Vite dev server proxies `/agent`, `/regions`
and `/health` to the backend at `http://localhost:8000` (see
`frontend/vite.config.ts`). If your backend runs elsewhere, set `VITE_API_BASE`
(e.g. in a `frontend/.env` file) or adjust the proxy target.

Build for production:

```bash
npm run build
```

## Data pipeline

The pipeline produces the three datasets the agent queries, from **real public
data plus realistic synthetic additions**:

```bash
python3 data/ingestion/run_pipeline.py     # from the repo root
python3 data/ingestion/build_sqlite_db.py  # load CSVs into data/luminalix.db
```

Steps (in order): process COVID-19 data → process WHO datasets (TB, malaria,
influenza) → generate synthetic diseases → combine into
`regional_survey_data` → generate hospital admissions → generate resource
allocation.

Current dataset (94 rows, 30 regions, 21 countries, 7 diseases):

| Disease        | Source    | Rows |
| -------------- | --------- | ---- |
| COVID-19       | real      | 20   |
| Tuberculosis   | real      | 20   |
| Influenza      | real      | 20   |
| Malaria        | real      | 17   |
| HIV            | synthetic | 8    |
| Lassa fever    | synthetic | 5    |
| Ebola          | synthetic | 4    |

`region` is the consistent join key across all three tables. Source licensing
is documented in `data/raw/ATTRIBUTION.md`.

## DataHub integration (implemented)

DataHub is the context layer for the project and the integration is **fully
implemented**, not stubbed:

- **`datahub_client.py`** drives the DataHub MCP server (`mcp-server-datahub`)
  over stdio and performs real dataset-level operations: `search` +
  `get_entities` + `list_schema_fields` to read schema, current description,
  and last-modified; `update_description` to **write findings back** as
  discoverable annotations on the `regional_survey_data` dataset entity
  (capped at the 10 most recent findings).
- **`data_access.py`** reads region-level values (survey staleness, admissions
  trends, resource levels) directly from SQLite, because DataHub's MCP tools
  don't return row-level data — the same architectural split a production
  DataHub deployment would have with a warehouse client alongside DataHub.
- **`data/ingestion/`** contains DataHub ingestion recipes; the working one is
  `recipe_sqlite_all_datasets.yml` (SQLite source → DataHub REST sink).

### Running local DataHub

DataHub runs via Docker Compose. The local compose file ships the whole stack
(GMS, frontend, Kafka, MySQL, OpenSearch) with **metadata-service auth
enabled**, so the GMS is reachable at `http://localhost:8080` and the UI at
`http://localhost:9002`:

```bash
datahub docker quickstart -f <path to your local compose file>
```

> **Important caveat**: running plain `datahub docker quickstart` without the
> `-f` flag re-fetches DataHub's default compose file from GitHub and silently
> resets `METADATA_SERVICE_AUTH_ENABLED` back to `false`, which would disable
> token auth. Always start DataHub with `datahub docker quickstart -f <path to
> your local compose file>` (e.g. `-f ~/.datahub/quickstart/docker-compose.yml`)
> so your edited file — and its auth settings — are what actually runs.

Generate a **personal access token** in the DataHub UI
(Settings → Access Tokens) and set it as `DATAHUB_TOKEN` in `backend/.env`.
This is required — the MCP server authenticates to GMS with this token and will
not start without it.

After starting DataHub, ingest the datasets once:

```bash
datahub ingest -c data/ingestion/recipe_sqlite_all_datasets.yml
```

## Backend API contract

| Endpoint                 | Description                                                              |
| ------------------------ | ------------------------------------------------------------------------ |
| `POST /agent/run`        | Trigger the agent loop as a background task. Returns `202` + `AgentRunStatus`. |
| `GET /agent/status`      | Current `AgentRunStatus` (`idle` / `running` / `complete` / `error`).     |
| `GET /regions/vulnerable`| Latest `VulnerableRegionsReport`. Filters: `?min_level=Low\|Moderate\|High` (default `Moderate`), `?country=...`. |
| `GET /regions/{region_id}` | Single `RegionAssessment`, `404` if not found.                          |
| `GET /health`            | Liveness check.                                                          |

## Data schema

The schema below is identical across the backend (Pydantic), the frontend
(`frontend/src/types/region.ts`), and the examples (`examples/`).

```
RegionAssessment:
{
  "region": string,            // e.g. "Bauchi, Nigeria"
  "country": string,           // e.g. "Nigeria"
  "disease": string,           // e.g. "Lassa fever"
  "vulnerability_level": "Low" | "Moderate" | "High",
  "justification": string,     // 1-3 sentences, plain language
  "confidence": "Low" | "Medium" | "High",
  "key_signals": string[],     // e.g. ["survey stale 42 days", "admissions +38% over 14 days"]
  "days_stale": integer,
  "flagged_at": string         // ISO 8601 timestamp
}

VulnerableRegionsReport:
{
  "generated_at": string,                       // ISO 8601
  "total_regions_evaluated": integer,
  "total_flagged": integer,
  "regions": RegionAssessment[]                 // sorted: level desc, then days_stale desc
}

AgentRunStatus:
{
  "status": "idle" | "running" | "complete" | "error",
  "started_at": string | null,
  "completed_at": string | null,
  "error_message": string | null
}
```

## Model

The reasoning agent uses `gemini-3.5-flash` by default (see `GEMINI_MODEL` in
`backend/.env`). The model runs through Vertex AI using Application Default
Credentials. The caller retries transient 429/503 errors with exponential
backoff, so quota/availability hiccups don't fail a run outright.
